Especificación Técnica del Motor de Validación Documental

Este documento describe el flujo de validación automática para los expedientes de préstamos de planes Cíes y Ons mediante procesamiento concurrente por Inteligencia Artificial y la integración con el backend de Odoo 16.

1. Flujo de Procesamiento y Ejecución en GPU

La validación de expedientes de crédito (ej. archivos PDF) se realiza renderizando las páginas a imágenes de alta definición (200 DPI) para posteriormente ejecutar análisis concurrentes utilizando el modelo de lenguaje de visión Qwen2.5-VL-8k operado localmente sobre Ollama. La detección de firmas y huellas es asistida por un modelo visual complementario YOLOv8.

2. Arquitectura de Despliegue y Contenedores

La solución se despliega utilizando Docker Compose sobre un servidor con GPU dedicada en el host remoto 172.17.0.33. La infraestructura está conformada por los siguientes contenedores:

odoo_ocr_engine

Microservicio FastAPI

Controla el ciclo de procesamiento de archivos. Recibe las llamadas REST, gestiona el hilo de paralelización con 4 trabajadores del pool, y evalúa las expresiones regulares en validators.py. Posee montajes de volumen directa a los archivos de código para hot-reload.

odoo_ocr_ollama

Servidor de Inferencia Ollama

Contenedor configurado con la biblioteca CUDA de Nvidia (Count: All) para transferir la carga de cómputo a la GPU NVIDIA RTX 5080. Carga el modelo de visión qwen2.5vl-8k y admite ejecución paralela mediante configuración de variables de entorno.

3. Matriz de Reglas de Validación (13 VL)

Las siguientes reglas se ejecutan de manera lineal en la función principal del backend. Cada regla se clasifica según su criticidad:

Código Regla Severidad Especificación de Validación en Código
VL-01 Cédula / Datos del cliente Error Regex robusto para cédulas panameñas. Retorna la primera coincidencia del cliente principal.
VL-02 Motivo de préstamo Error Comprueba presencia de etiqueta y valor de tipo de préstamo; ignora nombres y firmas.
VL-03 Seguro Social (NSS) Error Valida estructura de NSS, tolera valor genérico de planilla 0999-9999.
VL-04 Referencias Error Busca de forma independiente referencias bancarias y personales. Reporta faltantes específicos.
VL-05 Posición / Cargo Error Aísla el cargo real de la tabla de datos laborales. Excluye clasificaciones como "Gobierno/Privado".
VL-06 Sueldo / Rango Salarial Error Extrae rangos salariales explícitos o montos sueltos >= 100.00. Prioriza formato rango.
VL-07 Lugar de nacimiento Error Busca y valida coincidencia contra el catálogo oficial de provincias y comarcas de Panamá.
VL-08 Efectividades Aviso Confirma la presencia física del campo para que el oficial valide manualmente que no esté vencido.
VL-09 Firma en cotización Error Si se detecta cotización en el expediente, valida que exista al menos una firma del oficial autorizada.
VL-10 Número de planilla Error Identifica números de nómina (ej. P0800013010 o 8-21-06-0-01979). Excluye cédulas duplicadas.
VL-11 Longitud de dirección Aviso Verifica que la dirección residencial no exceda 120 caracteres. Exige un mínimo de 10 caracteres.
VL-12 Información de cónyuge Error Si el estado civil es Casado/Unido, exige datos del cónyuge. Filtra textos dummy del OCR.
VL-13 Proximidad huella-firma Aviso Mide distancia en px entre centros de Bboxes de YOLOv8. Falla si faltan firmas o huellas.

4. Registro de Cambios y Modificaciones (21/06/2026)

Bitácora cronológica de adecuaciones de infraestructura, optimizaciones del prompt y refactorización de código ejecutado durante el día de hoy.

Configuración de GPU Dedicada y Corrección de Errores de API 21/06/2026

Descripción del problema: Ocurrencia del error 400 Client Error: Bad Request de forma constante en el endpoint de chat de Ollama. Cuelgues sistemáticos del contenedor local por agotamiento de memoria RAM/CPU al procesar de forma secuencial múltiples imágenes de alta resolución provenientes de PDFs de gran tamaño.

Acciones técnicas ejecutadas:

  • Migración del motor de inferencia al servidor remoto 172.17.0.33 provisto de una GPU Nvidia RTX 5080 (16GB VRAM).
  • Edición del Docker Compose para integrar las reservas del driver nvidia y la API de GPU en los contenedores ollama y ocr_engine.
  • Parcheo de dependencias de python en la inicialización: se removió el cliente de OpenAI debido a conflictos de versiones con httpx y se implementaron peticiones JSON planas usando la librería nativa requests de Python.
Habilitación de Procesamiento Concurrente (ThreadPoolExecutor) 21/06/2026

Descripción del problema: Latencia excesiva en el procesamiento de expedientes (más de 5 minutos para un PDF de 33 páginas), lo cual superaba los límites de tiempo de transacción (timeouts) configurados en Odoo y bloqueaba al oficial de crédito.

Acciones técnicas ejecutadas:

  • Inyección de la variable de entorno OLLAMA_NUM_PARALLEL=4 para habilitar la cola de procesamiento en paralelo interna en Ollama sin encolar las peticiones.
  • Refactorización de `services.py`: Sustitución del ciclo imperativo for por un pool de hilos usando ThreadPoolExecutor(max_workers=4), mandando a analizar en paralelo las páginas del documento.
  • Control robusto de excepciones por hilo para asegurar que el fallo aislado de análisis de una página no interrumpa la extracción de texto del resto del expediente.

Resultado medido: El análisis del PDF de prueba de 33 páginas bajó de 300 segundos a **54 segundos** en total.

Restricciones de Contexto en Prompts y Mitigación de Alucinaciones 21/06/2026

Descripción del problema: Ollama extraía datos de nombres de referencias, firmas manuscritas o nombres de cónyuges descritos en copias de cédula secundarias o reportes APC y los asignaba de forma incorrecta como la Dirección Residencial o los datos principales del cónyuge, generando falsos errores de validación.

Acciones técnicas ejecutadas:

  • Se actualizó el System Prompt en `services.py` definiendo **reglas explícitas de exclusión por página**: se le instruye formalmente al modelo que la Dirección Residencial solo debe extraerse de la página con la cabecera `DATOS RESIDENCIALES`, devolviendo obligatoriamente `"NO ENCONTRADO"` en cualquier otra página del PDF.
  • Se aplicó la misma regla restrictiva al cónyuge, anclando su extracción a la sección formal de `INFORMACIÓN DEL CÓNYUGE` de la página de solicitud principal.
  • Afinamiento del prompt de cónyuge para obligar a extraer la cédula escrita a mano en la tabla (`8-724-379`), mitigando el error de buscar el documento físico de cédula.
Refactorización y Limpieza de Algoritmos en validators.py 21/06/2026

Descripción del problema: El parser de Python carecía de mecanismos para sanear las respuestas del LLM, reportando como válidos textos dummy del OCR o confundiendo cédulas con planillas y tipos de cliente con posiciones.

Acciones técnicas ejecutadas:

  • Función is_dummy_value: Se implementó un algoritmo centralizado de filtrado en el backend que identifica y anula respuestas dummy (ej. `"NOT A PICTURED DOCUMENT"`, `"NO ENCONTRADO"`, `"NINGUNO"`, `"N/A"`).
  • Normalización OCR: Creación de `normalize_ocr_text` para unificar minúsculas, remover acentos y corregir errores tipográficos conocidos en la salida del OCR (ej. unificar `0posicion` a `oposicion`).
  • Ajuste VL-01 (Cédula): Se limita el reporte a la primera cédula encontrada para evitar incluir cédulas secundarias detectadas en copias adjuntas.
  • Ajuste VL-05 (Cargo): Se limpiaron prefijos de cliente ("Gobierno", "Privado", "Independiente") para capturar la ocupación concreta.
  • Ajuste VL-10 (Planilla): Soporte de planilla de colaboradores gubernamentales (`8-21-06-0-01979`) y exclusión explícita de cédulas dentro del array de candidatos de planilla.
  • Ajuste VL-11 (Dirección): Se configuró un límite de longitud mínima de 10 caracteres para evadir falsos positivos cortos como nombres o firmas de páginas secundarias.
  • Ajuste VL-13 (Proximidad): Se reestructuró la evaluación de YOLO: si no se detectan firmas o huellas, la validación falla explícitamente (`passed=False`) reportando la alerta con severidad "Aviso", en lugar de retornar True.
